# 把一个版本交出去

发布前，我希望先确认三件事：包里装的是准备交出的代码，介绍写的是已经具备的能力，接手的人能知道如何使用，也知道何时应该停下来。

## 当前状态

版本为 0.7.0，处于发布准备阶段。仓库已有本地打包入口，尚未配置公开仓库地址，也没有创建远端 Release 或提交集市收录。

作者沿用已有署名 `SSZM`。没有确认的主页、支持邮箱、捐赠链接和远端地址保持空缺，不填示例地址冒充正式信息。

## 准备代码与资料

1. 同步 `plugin.json` 与 `package.json` 的版本，更新 CHANGELOG，确认中英文介绍、兼容范围与限制仍属实。
2. 确认目录名、两份清单的 name 都为 `siyuan-plugin-chord`。若迁移旧原型，保留禁用旧包及状态不自动迁移的说明。
3. 核对图标、预览和 README。示意图保留标识，不能换个标题充当实际截图。真实截图须只含经允许公开的演示内容。
4. 在本地执行基础测试、仓库检查、浏览器回归。涉及交互的修改还要做双前端实测。记录实际测试环境与跳过项。

```sh
npm test
npm run check
npm run test:browser
```

## 打包

在 Windows 项目根目录执行：

```sh
npm run build
```

输出是 `dist/package.zip` 和 `dist/package.zip.sha256`。版本从 `plugin.json` 读取；压缩包名称固定，便于按思源集市约定上传。文件由 `package.json` 的 files 白名单指定，ZIP 根目录直接包含 `plugin.json`，没有包裹目录。测试、脚本、Git 与 IDE 文件不进入包。

脚本先执行仓库检查，再创建临时 ZIP；逐项比较归档文件与源文件哈希，核对完整后才替换最终产物。请只上传生成的包，不要把整个项目文件夹临时压缩后发布。

## 公开发布之前

确定真实 GitHub 仓库后，将 `plugin.json.url` 填为该仓库的 HTTPS 地址，并设置 Git remote。然后执行：

```sh
npm run check:release
```

这个检查会在地址空缺、占位或仓库名不符时失败。失败表示公开资料尚未填妥，不影响本地测试和打包。它不核验 GitHub 仓库是否真实存在、不替代浏览器测试，也不自动发布。

确认远端仓库、作者信息和待发布提交无误后，再为最终提交创建版本标签并创建对应 GitHub Release，将 `package.zip` 与校验文件作为附件。首次公开发布时，把 CHANGELOG 的“准备中”改为实际发布日期；不要提前填写下载量、用户数或尚未发生的发布日期。

思源当前官方示例要求默认分支为 `main`，插件 name 唯一并与仓库名一致，以对应版本标签的 Release 附带 `package.zip`；提交集市前应重新核对官方规则，并在集市列表确认包名尚未占用，按真实仓库地址申请收录。相关原始资料为 GitHub 上的 `siyuan-note/plugin-sample` 与 `siyuan-note/bazaar`。

## 安装验收

用生成的 ZIP 安装到测试工作区，确认包名、中文“和弦”与英文“Chord”显示正确；再用同一内核的两个窗口验证状态、编辑、保存、撤销和禁用清理。旧原型必须先禁用。

最后核对原始源码与 ZIP 内的运行文件一致。发布说明写清已验证环境、个人历史在刷新后清空、复杂事务暂不支持，以及前端锁的实际边界。

## 对外介绍的口吻

写给一个正在处理笔记的人，而不是给搜索词凑一页说明。

先讲他会遇到的事情，再讲和弦如何处理。少用“极致”“无缝”“革命性”一类无法核对的词。功能写到具体动作，限制写到具体后果；错误提示给下一步，不把责任推给使用者。

可以写“你可以先选中文字，准备好了再双击编辑”。不要把它抬高成“重新定义协作”。一款还在成长的插件，把自己交代清楚，已经值得认真对待。
